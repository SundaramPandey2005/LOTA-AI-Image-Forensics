LOTA Project — Targeted Iteration 2.1 Fixes

The previous iteration made genuine progress, especially on database provenance separation. Do not redesign the project, expand the scope, add new features, or begin another broad audit.

Instead, make the following three targeted corrections based on verification of the actual implementation and generated artifacts.

The goal of this iteration is:

Ensure that every value labeled as paper-derived actually matches the LOTA ICCV 2025 paper, and ensure that no synthetic visualization or fallback output can be mistaken for real GenImage analysis.

Follow the existing architecture and research-integrity principles.

1. Correct the Published Reference Benchmark Data
Important rule

Anything stored as:

source_type = 'published_reference'

must be directly traceable to the ICCV 2025 LOTA paper.

Do not use approximate values, remembered values, interpolated values, values from a different table/row, or values generated by previous code.

The paper itself is the source of truth.

1.1 Audit scripts/seed_reference_data.py

Review every number currently inserted into:

reference_benchmarks

For each value:

Identify the exact paper table.
Identify the exact row/method.
Identify the exact generator/column.
Verify the transcription against the provided research paper.
Add enough metadata so the origin of the reference is clear.

For example, reference records should ideally be traceable through fields or metadata such as:

paper_table
paper_method
training_generator
evaluation_generator
metric

Do not invent schema complexity unnecessarily, but the source of every published number must be reconstructable.

2. Fix the GenImage Visualization and Synthetic Fallback Behavior

The previous iteration claimed that the forensic validation notebook performed analysis on real and AI-generated GenImage images.

However, inspection showed that the generated visualization artifact was still the old synthetic visualization.

The dataset was not actually available, and the notebook silently fell back to synthetic data.

This must be fixed because:

Synthetic verification is valid for mathematical testing, but it must never be presented as real-world forensic analysis.

2.1 Make the fallback explicit and impossible to miss

Locate the dataset-loading logic in:

notebooks/01_lota_mathematical_validation.ipynb

and any associated visualization scripts.

If GenImage data is unavailable, the notebook must display a highly visible warning.

For example:

WARNING: GenImage dataset was not found.

This notebook is currently running with synthetic verification samples.

The generated visualization validates the mathematical pipeline only.
It must NOT be interpreted as evidence of real-image or AI-generated-image forensic behavior.

Qualitative comparisons with Figure 3 of the LOTA paper are disabled until real GenImage samples are available.

This warning should be:

printed clearly in notebook output,
included in relevant visualization metadata or captions if appropriate,
reflected in markdown cells,
impossible to overlook during a demo.

Do not silently substitute synthetic data.

2.2 Separate synthetic validation from real-data validation

The notebook should explicitly support two modes.

Mode A — Synthetic Mathematical Validation

Purpose:

Verify implementation correctness.

Examples:

controlled gradients,
synthetic bit patterns,
directional edges,
localized high-frequency artifacts.

Allowed conclusions:

The implementation behaves mathematically as expected.
MGPS selects the expected high-gradient region.
Bit-plane decomposition reconstructs correctly.

Not allowed conclusions:

Fake images exhibit this behavior.
Real images exhibit this noise distribution.
Results are consistent with Figure 3 on real data.
Mode B — Real GenImage Forensic Validation

Once a minimal GenImage subset is available, the notebook must explicitly load:

at least one real image,
at least one AI-generated image,

preferably corresponding to a clearly documented generator source.

The visualization should then show a comparable pipeline for both samples:

Original Image
        ↓
Bit-Plane Decomposition
        ↓
Low-Bit Composition / Noise Representation
        ↓
Normalization
        ↓
MGPS Gradient Map
        ↓
Selected Patch

Clearly label:

REAL SAMPLE
AI-GENERATED SAMPLE
Generator: <name>
Dataset source: GenImage

Only after real samples are actually processed may the notebook include a qualitative discussion comparing observations with Figure 3 from the LOTA paper.

The comparison should use careful language such as:

"Our sample qualitatively shows..."
"Consistent with the type of visual distinction illustrated in Figure 3..."
"Observed on this sample; not sufficient to establish a statistical conclusion..."

Do not make broad claims from one or two images.

2.3 Do not overwrite synthetic artifacts ambiguously

The existing:

forensic_decomposition.png

was found to be identical to the previous synthetic visualization.

Fix the artifact handling.

Use clearly separated names, for example:

forensic_decomposition_synthetic.png

The filename itself should communicate provenance.
